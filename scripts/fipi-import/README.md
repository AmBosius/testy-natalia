# Импорт заданий по русскому языку из открытого банка ФИПИ

Три (плюс один опциональный) шага, каждый — отдельный скрипт, чтобы можно
было перезапускать любой из них по отдельности.

## Разведка (сделана руками, через Network-вкладку браузера)

Источник данных:

```
GET https://{ege|oge}.fipi.ru/bank/questions.php?proj=<GUID предмета>&page=<N>&pagesize=100
```

- HTML-фрагмент с пачкой заданий (сервер сам режет по 100 максимум за раз, `page` с 0).
- Пустая пачка — конец списка.
- GUID предмета "Русский язык": ЕГЭ `AF0ED3F2557F8FFC4C06F80B6803FD26` (2140 заданий),
  ОГЭ `2F5EE3B12FE2A0EA40B06BF61A015416`.
- Кодировка ответа — `windows-1251` (см. `Content-Type` заголовок).
- `robots.txt` на обоих доменах отсутствует (404).

Каждое задание — `<div class="qblock" id='q{short_id}'>` (текст, варианты,
инпуты) плюс соседний `<div id='i{short_id}'>` со свойствами (КЭС-код —
это и есть тема по классификатору ФИПИ, и тип ответа).

Некоторые `qblock` — не задания, а общий текст-отрывок для группы вопросов
(напр. задания 22–26 ЕГЭ): без `id` и без `guid`/формы, только текст. Идут
в документе перед вопросами, которые к ним относятся — `fetch_fipi.py`
ловит это и прикрепляет как `passage_text` к следующим настоящим вопросам.

### Главное ограничение источника

**ФИПИ нигде не публикует правильные ответы.** Проверка идёт на сервере
(`solve.php`), клиенту возвращается только код 0/1/2/3
("не решено/неверно/решено/верно") — сам правильный вариант не передаётся
ни в HTML, ни в каком-либо AJAX-ответе. Проверено на ЕГЭ и ОГЭ — одинаково.
Это не баг скрапера, это архитектурное решение сайта (иначе теряется смысл
самопроверки). Поэтому:
- `fetch_fipi.py` / `map_schema.py` физически не могут взять `correct`
  из первоисточника — только текст, варианты и классификацию.
- Опциональный `llm_answer.py` восполняет это через LLM (см. ниже) —
  ответы **не** гарантированно верны, это эвристика модели, не факт с сайта.

## Шаг 1 — `fetch_fipi.py` (сырой JSON)

```bash
python fetch_fipi.py --exam both --out-dir data/raw
# или по отдельности:
python fetch_fipi.py --exam ege --out data/raw/rus_ege_raw.json
python fetch_fipi.py --exam oge --out data/raw/rus_oge_raw.json
```

Складывает как есть: текст задания (HTML + чистый текст + абзацы отдельно),
варианты ответов (если это выбор), тип инпута (`text`/`checkbox`/`radio`/
`select`/`unknown`), КЭС-классификатор, метку типа ответа с сайта,
привязанный текст-отрывок (`passage_text`), полный/короткий id задания.

Пауза 0.6с между запросами — вежливый краулинг, не DDoS.

## Шаг 2 — `map_schema.py` (разметка под схему)

```bash
python map_schema.py --in data/raw/rus_ege_raw.json data/raw/rus_oge_raw.json \
    --out data/final/rus_final.json
```

Регэксп-эвристики по ключевым словам (`classify_type`) сортируют задания
по 4 типам схемы:
- `checkbox`/`radio` → `choice`
- `select` (задание 8 ЕГЭ, установление соответствия) → `digits`, порядок важен
- текстовый ответ + слово "цифр…" → `digits` (набор без порядка, если это
  не "соответствие")
- текстовый ответ + "найдите/укажите номер... предложени..." → `sentence-number`
- текстовый ответ, всё остальное → `word` (дефолт для краткого ответа)

Эссе ("Развёрнутый ответ") и "Расстановка терминов" ни в один из 4 типов
не укладываются — пропускаются (остаются в сыром JSON, ничего не теряется,
статистика пропусков печатается в конце).

`text`/`passage` разводятся эвристически: если у абзацев есть явные
маркеры `(1) (2) (3)…`, всё до первого такого абзаца — инструкция (`text`),
он сам и дальше — `passage`. Не удаётся разделить надёжно — не гадаем,
всё уходит в `text`, `passage: null`.

`level` (1/2/3) — **грубая эвристика**, не с сайта: у ФИПИ нет фильтра
сложности для русского языка. ОГЭ = 1, ЕГЭ с выбором/кратким ответом = 2,
ЕГЭ с сопоставлением = 3. Стоит перепроверить вручную для реальных тестов.

`test_title` — тоже эвристика: "ЕГЭ/ОГЭ. Русский язык — {первая тема КЭС}".
Это черновая группировка, не готовая структура тестов — Наталье (или ещё
одним проходом скрипта) стоит перегруппировать по смыслу.

`correct: []`, `needs_review: true` — всегда, см. ограничение источника выше.

## Шаг 3 (опционально) — `llm_answer.py` (LLM определяет ответы)

Сайт ответы не даёт → достаём их через LLM. Использует тот же прокси
(Токенатор), ключ берётся из `E:\Работы\lead-pipeline\.env` (`LLM_API_KEY`).

**Важно про эндпоинт**: `LLM_BASE_URL` из `.env` (`.../anthropic`) —
Anthropic-совместимый `/v1/messages`, он только для моделей Claude.
Для не-Claude моделей (DeepSeek, Qwen и т.п.) у Токенатора отдельный
OpenAI-совместимый путь `https://api.tokenator.top/v1` + `/chat/completions`
— именно его использует `llm_answer.py` по умолчанию (`--base-url`).
На `/v1/messages` с не-Claude моделью Токенатор отвечает 503
`overloaded_error` независимо от имени модели (проверено даже на
заведомо несуществующей) — это generic "эта модель тут недоступна",
а не хинт про опечатку.

Модель — **не Claude**, дешёвая/быстрая (нагрузка механическая, 1000+
заданий): по умолчанию `deepseek-v4.1-flash` (id подтверждён на
tokenator.top/models и в `/status`). У неё **reasoning включён по
умолчанию** (effort=high) — без отключения модель тратит весь
`max_tokens` на цепочку рассуждений и не успевает выдать JSON
(`finish_reason: length`, пустой `content`). Поэтому в запрос всегда
добавляется `"thinking": {"type": "disabled"}` — с ним один вопрос
обрабатывается за ~2-5 секунд вместо десятков.

Если модель/эндпоинт не отвечают — скрипт сначала гоняет смоук-тест на
1 задании и останавливается с понятной ошибкой, не тратя запросы на
весь `--limit`.

```bash
python llm_answer.py --in data/final/rus_final.json \
    --out data/final/rus_final_llm.json --limit 80
```

`--limit 80` — по умолчанию первые ~80 заданий (это и есть стартовые
15-20 тестов), остальное доразмечается по мере необходимости повторным
запуском с бОльшим `--limit` (уже размеченные, у кого есть `_llm_model`,
повторно не трогаются).

Прогон навешивает `correct`/`needs_review`/`confidence` от модели плюс
служебные `_llm_confidence`/`_llm_model` для трассировки. **Это ответы,
определённые ИИ по правилам, а не выгруженные с сайта** — для реального
использования в тестах Наталье стоит выборочно перепроверить, особенно
всё с `confidence: "low"` или `needs_review: true`.

## Итоговые файлы

- `data/raw/rus_ege_raw.json`, `data/raw/rus_oge_raw.json` — шаг 1, сырьё
  на всякий случай (перепроверка, доразбор пропущенных эссе/сопоставлений).
- `data/final/rus_final.json` — шаг 2, финальная схема без ответов.
- `data/final/rus_final_llm.json` — шаг 3, с ответами от LLM (опционально).
